# MVP: этапы, бюджет, риски и решения

Дата: 26 октября 2026. Статус: предложение до начала программирования. Все оценки труда и производства — инженерные допущения; суммы ниже не являются разрешением их потратить.

## 1. Рекомендуемый объём

- Одна оригинальная законченная история на **60–120 секунд**; целиться в 90 секунд.
- Два постоянных оригинальных персонажа; третий только после успешной версии с двумя.
- Одна основная локация, один конфликт, понятная эмоциональная развязка.
- Ориентир 12–24 плана и 6–10 смысловых beats; количество не является самоцелью.
- Minecraft Java с ванильным видом мира, без shaders и сложных эффектов на старте.
- Без диалогов, субтитров и обязательных для понимания надписей. Звуковые события и музыка допустимы.
- Проверенные движение, взгляд, поворот, пауза и простые реакции; предметы и server events — только после технической приёмки.
- Финал 1920×1080, 30 fps, H.264/yuv420p, звук 48 kHz. Если 1080p не проходит ранний benchmark, изменение целевого профиля согласуется до приёмки, а не маскируется апскейлом.
- Никаких драк, сложного parkour, жидкостей, взрывов, толпы, процедурных огромных миров и произвольного переноса motion из видео.

Сначала делается один убедительный эталон с допустимой ручной режиссёрской доработкой. Только после его понятности автоматизируется устойчивый процесс. Финальная автоматическая приёмка выполняется на зафиксированном brief и подготовленных assets без ручной правки сгенерированного сценария, keyframes и монтажа в ходе контрольного прогона.

## 2. Этапы и точки остановки

Трудоёмкость — для одного опытного разработчика с доступом к творческой обратной связи. Дни — рабочие, не обещанные даты.

| Этап | Работа и артефакт | Условие перехода | Оценка |
|---|---|---|---|
| 0. Фиксация решений | BudgetGrant, выбранный backend-кандидат, refs, герои, понимание staged/server режима | Решения из раздела 7 согласованы | 1–2 дня |
| 1. Проверка съёмочных возможностей | 10–15 секунд: 2 актёра, реакция, предмет/server event, камера, звук, reset; 3 повтора | Видимое действие, общие часы, повторяемость, 1080p; ограничения зарегистрированы | 3–5 дней |
| 2. Библиотека исполнения | 8–12 простых primitives, CharacterBible, LocationSpec, capability registry, тесты ракурсов | Не менее 8 выразительных проверенных primitives, нет выдуманных возможностей | 4–6 дней |
| 3. Референсы и KB | 4–6 клипов, структурированные наблюдения, 10+10 карточек, отложенная проверка | Источники/таймкоды/неопределённость сохранены, существенные ошибки исправлены | 3–5 дней |
| 4. Одна история и режиссёрский эталон | 3 логлайна → один сюжет → подробная раскадровка → 540p animatic | Пробные зрители понимают конфликт/развязку; выразительность достаточна | 4–6 дней |
| 5. Автоматизация производства | Контракты, compiler/preflight, задания, renderer, editor, manifests и budget ledger | Воспроизведение и сборка принятого плана без GUI-ввода, сбои восстанавливаются | 4–7 дней |
| 6. Критик и локальные исправления | Слепой просмотр, отчёт, маршрутизация дефектов, один полный цикл selective render | Конкретный дефект обнаружен, исправлен и перепроверен в пределах лимита | 4–6 дней |
| 7. Контрольный прогон | Фиксированные исходные assets, AI-сценарий/режиссура, 1080p master, отчёт, зрители | Все критерии раздела 3; никаких скрытых ручных правок | 2–4 дня |

Итого **25–41 рабочий день**, примерно 5–8 полных рабочих недель; с неполной загрузкой, ожиданием тестов и запасом на BBS — планировать **7–11 календарных недель**, ориентировочно **220–360 часов**. Это порядок величины для ограниченного MVP, а не оценка студии для 15-минутных эпизодов. Провал раннего технического эксперимента требует новой оценки.

Правила остановки:

- Этап 1 не даёт читаемой реакции/синхронизации — ограничить выразительность/режим или выбрать другой backend. Не строить остальной конвейер на непроверенной возможности.
- Эталон этапа 4 скучен/непонятен — доработать сюжет и постановку. Полная автоматизация не должна закрепить плохой эталон.
- Исправления не улучшают результат после двух попыток — передать на человеческую оценку.
- Рост длительности запрещён до принятого пилота; затем несколько коротких историй, потом 3–5 минут и только после этого 10–15.

## 3. Точные критерии успеха первого MVP

### 3.1. Анализ референсов и библиотеки

1. Обработаны минимум 4 предоставленных клипа, минимум по 2 в каждом направлении, суммарно 15–30 минут выбранных фрагментов. Если доступны только короткие ролики, объём корпуса изменяется до старта, с перерасчётом бюджета.
2. Для **100% сохранённых выводов** есть источник/hash, interval, evidence, наблюдение отдельно от интерпретации, две уверенности, тип и воспроизводимость. Нет вымышленных таймкодов.
3. На двух отложенных фрагментах размечаются не менее 20 контрольных событий, включая хотя бы 10 реальных склеек. Не менее 90% обнаруженных контрольных границ попадают в ±2 исходных кадра; precision и recall границ оба ≥0,85. Ложные склейки от движения/вспышек учитываются.
4. Из 20 проверенных описаний событий не менее 17 соответствуют видимому материалу по разбору двух рецензентов. Спорные случаи получают uncertain и не засчитываются как уверенно верные.
5. Есть ≥10 разных сценарных и ≥10 постановочных карточек с provenance; минимум 3 карточки каждого вида применены в собственном пилоте с зафиксированным результатом. Это не требование автоматически подтвердить все 20 карточек зрителями.

### 3.2. История и раскадровка

1. История 60–120 секунд, 2–3 героя, 1–2 локации, один основной конфликт и завершённая развязка.
2. Нет зависимости от человеческого языка; весь обязательный смысл задан действиями, изображением и звуком.
3. Для **100% critical beats** указаны цель, причина/следствие, зрительское понимание, видимые cues, план/планы, длительность и проверка читаемости.
4. Все critical actions существуют в принятом CapabilityProfile и проходят preflight. Нет тихой замены ключевого действия несовместимым упрощением.
5. Финальная развязка имеет показанную подготовку; критическая причинная цепь не содержит неразрешённых StoryReview blocker.

### 3.3. Исполнение и техническое качество

1. Все финальные визуальные планы сняты в настоящем Minecraft; master прослеживается до take, snapshot, версии backend и StorySpec. Нет сгенерированного вне игры финального видеоряда.
2. 1920×1080, 30/1 fps, полный decode без ошибок, точное количество кадров по EditManifest. Допуск A/V-длительности — один видеокадр с учётом padding кодека.
3. Ноль непреднамеренных чёрных/пустых кадров, пропавших героев в critical action, camera-through-wall и пропущенных server events. Творческие затемнения допускаются только как записанное решение плана.
4. Все critical events выполнены не позднее одного production tick от расписания; связанный звуковой onset — не далее 2 видеокадров от запланированного момента.
5. Критические предметы/действия видны не менее заданного в ShotSpec времени; baseline для важного reveal — 0,7 секунды, исключения заранее обоснованы.
6. Один 10–15-секундный тестовый take повторён 3 раза из одного snapshot: позы в контрольных точках расходятся не более 0,05 блока/2°, ключевые события — не более 1 тика. Изображения могут различаться из-за рендера; MP4-хеш не критерий.
7. Пройдены ранний отказ FFmpeg, отмена, неправильный JSON, duplicate delivery, перезапуск клиента и следующий успешный render. Частичный результат не объявляется успехом.

### 3.4. Критик и исправления

1. VideoReview имеет девять отдельных художественных измерений: понимание, причинность, выражение, анимация, камера, монтаж, темп, интерес и соответствие сценарию. У каждого дефекта есть evidence/timecode и вероятный исправляющий модуль.
2. Слепая реконструкция получена **до** выдачи критику сценария. Невозможность понять эпизод не скрывается высоким соответствием тексту.
3. Подготовлен калибровочный набор из 20 коротких отрывков собственного производства: 10 с известными major-дефектами, 10 чистых. Критик находит ≥8 из 10 дефектов и делает ≤2 ложных major-срабатываний на чистых. Заранее созданные ошибки помечены как искусственные. Этот тест проверяет диагностику, не «умение измерять юмор».
4. Система автоматически исправляет минимум один намеренно внесённый поддерживаемый дефект — например, перекрытие цели камерой или преждевременную склейку — и пересобирает master. Проверка показывает устранение дефекта; это интеграционное доказательство repair-механизма.
5. Натуральные дефекты финального эпизода также анализируются; отсутствие поддержанного способа исправления приводит к честному `needs_human_review`. Сам по себе успех на искусственной ошибке не делает пилот принятым.
6. Соблюдены лимиты: ≤2 переработок StorySpec, ≤2 локальных исправлений одного кадра, ≤2 полных видеопроходов исправления; ни один cap расходов не превышен.

### 3.5. Зрительская приёмка — обязательная

До финального теста фиксируются пять вопросов, допустимые ответы и целевая эмоция; затем они не подгоняются под ответы. Участники этапа разработки не входят в приёмочную группу.

Предложение для пилота: **12 новых зрителей**, не знающих сценария; минимум три языковые группы, минимум по три человека в каждой. Начальная проверка на взрослых; возраст основной аудитории — решение до программирования. Это небольшая проверка понятности, а не доказательство международного рыночного успеха.

- После первого просмотра финальной версии без подсказок: минимум **10 из 12** верно описывают цель, основной конфликт и развязку — по каждому из трёх пунктов отдельно.
- На пяти вопросах «почему/что изменилось» минимум **48 верных ответов из 60**, и минимум **9 из 12** зрителей верно отвечают хотя бы на 4 из 5.
- Целевую эмоцию/изменение отношений в финале считывают минимум **9 из 12** по заранее принятому ключу свободных ответов.
- Интересность: медиана ≥**4 из 5**, минимум **8 из 12** ставят 4 или 5. Для понятности и выразительности также медиана ≥4; для анимации, камеры, монтажа и темпа — ≥3,5, без major-дефектов по двум техническим рецензентам.
- При смене крупности/ракурса минимум **10 из 12** правильно различают обоих героев в контрольных кадрах.
- Два рецензента сопоставляют видео с планом: 100% critical beats присутствуют; несовпадения supporting beats перечислены и приняты явно.

Отчёт содержит сырые анонимные результаты, расхождения рецензентов и частые непонимания. LLM-score не отменяет провал человеческой приёмки. Повторный зрительский тест после существенных исправлений — на новой группе; число участников и стоимость учитываются отдельно.

### 3.6. Проверка автоматизации

После подготовки персонажей, площадки и primitives один контрольный production run выполняет цепь:

`refs/KB → оригинальная StorySpec → review → DirectionPlan → preflight → Minecraft takes → edit/sound → video review → ограниченный repair → master + report`.

В контрольном прогоне запрещены ручное управление игрой, подмена видео и ручная правка сценария/поз/монтажа. Разрешены предоставление brief/assets, явный budget grant, старт/отмена и финальная человеческая оценка. Все творческие ручные вмешательства в разработочный эталон перечисляются отдельно.

Бюджет соблюдён, все входы/выходы версионированы, потерянные этапы возобновляются. Целевой предел контрольного прогона после готовых assets — **2 часа** локального производства без Batch-ожидания; ≤15 минут операторского участия. Это целевой показатель, который измеряется, а не уже достигнутая производительность.

**MVP принят только при выполнении всех шести групп критериев.** Если автоматизация проходит, а история неинтересна зрителям, MVP не принят.

## 4. OpenAI API: расчёт стоимости

### 4.1. Проверенные тарифы и условия расчёта

На 26 октября 2026 официальная страница указывает следующие Standard-тарифы за 1 млн токенов. В таблице только некэшированный input/output; премиальные режимы не закладываются. [OpenAI API Pricing](https://developers.openai.com/api/docs/pricing).

| Модель | Input, USD/1M | Output, USD/1M |
|---|---:|---:|
| GPT-6 Luna | 0,10 | 0,50 |
| GPT-6.1 Sol | 2,00 | 10,00 |
| GPT-6 Astra | 10,00 | 50,00 |

Для Sol/Astra запросы свыше 272K input меняют тариф всего запроса. Поэтому здесь предполагаются короткие окна и каждый запрос <40K input. Биллинг image tokens зависит от модели, размера и detail; стоимость не равна фиксированной цене «за кадр». Выходной лимит должен учитывать оплачиваемые reasoning tokens. [Sol — тарифные условия](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [vision и image token accounting](https://developers.openai.com/api/docs/guides/images-vision).

Общая формула:

`API cost = Σ(input_tokens × input_rate + output_tokens × output_rate) / 1 000 000 + отдельно оплачиваемые modalities/tools`.

Кэш и Batch не учитываются как гарантированная экономия. Для независимых offline-анализов Batch может давать 50% скидки с окном выполнения до 24 часов; он не подходит для обещания двухчасового интерактивного цикла. [Официальный Batch API](https://developers.openai.com/api/docs/guides/batch).

### 4.2. Прозрачный сценарий первого пилота

Предполагаем 20 минут референсов и 90-секундный эпизод. **800 image tokens/кадр — расчётное допущение, не фиксированный тариф и не измерение.** До платного запуска размер/detail проверяются официальным калькулятором и прогнозом входа; после первого разрешённого малого прогона оценка заменяется actual usage.

Для референсов: 1200 поданных кадров с учётом повторов в перекрывающихся окнах ×800 =0,96M image tokens; ещё 0,18M текстового контекста/повторных сводок и 0,06M output. Для видеокритика — порядка 240 поданных кадров с плотной выборкой важных действий, плюс контекст. Эти цифры — объём отправки, не число уникальных кадров.

| Этап | Модель | Input, M | Output, M | USD |
|---|---|---:|---:|---:|
| Первичный анализ референсов | Sol | 1,14 | 0,060 | 2,88 |
| Story + Story Critic | Sol | 0,10 | 0,025 | 0,45 |
| Director и доработка плана | Sol | 0,15 | 0,040 | 0,70 |
| Первичный Video Critic | Sol | 0,30 | 0,030 | 0,90 |
| Два ограниченных repair-прохода суммарно | Sol | 0,50 | 0,080 | 1,80 |
| Необязательная экспертная эскалация | Astra | 0,08 | 0,015 | 1,55 |
| Нормализация/простые классификации | Luna | 0,30 | 0,040 | 0,05 |
| **Итого текст/изображения** | | | | **8,33** |

Audio-сценарий: условно 0,03M audio input tokens, 0,02M text input и 0,005M text output GPT-Audio-1.5. По тарифам $32/M audio input, $2,50/M text input и $10/M text output это **$1,06**. Число audio tokens здесь также допущение; не заявляется фиксированная цена за минуту не-речевого материала. Выходное аудио не генерируется. [Тарифы модели](https://developers.openai.com/api/docs/models/gpt-audio-1.5).

**Номинальный сценарий: $9,39 API за первый пилот вместе с первичным корпусом.** Если image token budget удвоится, добавится стоимость дополнительных входных токенов, а не удвоится весь счёт. Существенное увеличение числа окон, reasoning и повторов увеличит расходы сильнее; отсюда обязательный reserve и cap.

Практический плановый запас: **$15–30 на первый пилот**, включая повторные запросы в разрешённых пределах. Повторное использование готовой KB убирает исходный reference-analysis, но не review нового видео. Ориентир следующего короткого пилота — **$5–20 API** при том же ограниченном объёме; это оценка, не цена услуги.

10–15-минутный эпизод пока не бюджетируется как готовая производственная услуга. Грубый сценарий при похожей плотности кадров и доработок — **$50–300 API/эпизод**; доля связности и repair может расти нелинейно. Пересчитать можно только после коротких пилотов.

### 4.3. Предлагаемые лимиты первого эксперимента

Для отдельного согласования: общий максимум **$50**, из них до $10 — первоначальные референсы/KB, до $20 — каждый из двух pilot production runs. Это верхние лимиты, не обязательные расходы. Max cost одного запроса — $2; запросы дороже сначала разбиваются или требуют нового grant. Astra/audio разрешаются явно в списке моделей grant.

Система резервирует верхнюю стоимость **до** вызова, включая max output и повторные попытки. Параллельные запросы не могут по отдельности израсходовать один остаток. Фактическое usage сверяется с резервом; неизвестный результат после timeout остаётся зарезервированным до выяснения. Достижение cap завершает платную работу с отчётом.

Если текущие тарифы/модальности не позволяют честно вычислить верхнюю границу, вызов не отправляется. Нужна корректировка настройки или отдельное согласование. Автоматический переход на дорогую модель не допускается. Сейчас BudgetGrant отсутствует, расходы этой работы — **$0 платных OpenAI API-операций**.

## 5. Вычисления и производственные расходы

### Локальная станция

Предложение для испытания: одна графическая машина с 16 GB RAM минимум, предпочтительно 24–32 GB, SSD и не менее 50–100 GB свободного места. Это стартовый запас, не гарантированная минимальная конфигурация. Локальные модели не нужны; GPU занят Minecraft, CPU — decode/encode и обработкой медиа.

Пропускная способность raw RGB 1080p30: `1920×1080×3×30 = 186 624 000 байт/с`, около **187 MB/s**, или **16,8 GB за 90 секунд** без сжатия. Поэтому raw-кадры передаются в pipe; полные последовательности на диск сохраняются только для диагностики выбранных кадров.

При предположении H.264 8–20 Mbit/s финальные 90 секунд занимают примерно **90–225 MB**. CRF-экспорт не гарантирует этот bitrate. Дубли, proxies, frames и reference assets потребуют гигабайты; предложенный scratch-запас 50–100 GB снимает риск слишком раннего заполнения диска.

Планировать **2–6 машино-часов на короткий пилот в период отладки**, включая все preview, анализ медиа и пересъёмки. Затем цель контрольного цикла — ≤2 часов. Скорость старого 12-секундного 540p демо нельзя линейно переносить на новые миры, 1080p, звук и десятки планов.

Расчёт электричества только как пример: 0,10–0,25 kW ×2–6 ч =0,2–1,5 kWh. При **условной** цене $0,20–0,40/kWh — $0,04–0,60. Это не проверенный местный тариф.

### Облако

На старте не требуется. Нужна графическая среда, подходящая версия OpenGL/драйверов и проверенный backend. Если **для расчёта** принять $0,50–2/машино-час, то 2–6 часов стоят $1–12 плюс storage/egress. Это диапазон входных допущений калькулятора, не актуальная котировка провайдера; поставщик и цены не выбраны. Перенос с macOS на Linux/Windows требует собственной приёмки.

### Основная стоимость — подготовка и качество

| Статья | Плановая оценка | Комментарий |
|---|---|---|
| Реализация ограниченного MVP | 220–360 часов | Без обучения моделей и масштабирования |
| Денежная оценка труда | $7 700–28 800 | Только арифметика при условной ставке $35–80/ч; не рыночная котировка |

| Творческая проверка в разработке | Примерно 1–4 часа на итерацию пилота | Финальная автоматизация не отменяет затрат разработки эталона |
| Зрительская приёмка | $0 при добровольцах либо, например, $60–180 за 12 участников | Условное вознаграждение $5–15; не тариф исследовательской платформы |

Труд владельца при самостоятельной разработке не превращается автоматически в денежный платёж, но должен учитываться как время. Тариф API за несколько долларов не означает, что хорошая 90-секундная постановка стоит несколько долларов целиком.

## 6. Риски и способы ранней проверки

Оценки качественные, до испытаний.

| Риск | Вероятность / влияние | Ранний сигнал | Действие |
|---|---|---|---|
| Скучная, но формально связная история | Высокая / критическое | Зрители понимают, но не хотят досматривать | Эталон и зрители до полной автоматизации; причины выбора и эмоциональная цена |
| Эмоция требует недоступного рига | Высокая / высокое | «Улыбка»/«объятие» в плане без capability | Генерация внутри проверенных возможностей; тесты поз/паузы/крупности |
| Визуальные актёры не меняют мир | Высокая для текущего прототипа / высокое | Блоки/инвентарь расходятся с сюжетом | Раздельные staged/server actions, ack и snapshot |
| Рассинхронизация server/client/export/audio | Средняя–высокая / критическое | Событие или звук сдвигается при повторе | Общие часы, deterministic reset, ранний 3-take тест |
| Изменение внутренних BBS API | Средняя / высокое | Новый commit ломает сериализацию или export | Pin полного стека, узкий backend, контрактные проверки |
| Плохие траектории/камера/монтаж | Высокая / высокое | Перекрытие предмета, потеря экранной географии | Геометрический preflight, статичная камера по умолчанию, beat coverage |
| Модель выдумывает действия референса | Высокая / высокое | Интерпретация без evidence | Наблюдение/интерпретация отдельно, dense resampling, uncertain |
| Critic подтверждает свой же замысел | Высокая / высокое | Высокие баллы при непонимании зрителей | Blind reconstruction, разные контексты/модели, человеческие метки |
| Исправление портит другие кадры | Средняя / высокое | Предметы/позы расходятся после reshoot | Граф зависимостей, continuity, контроль соседей, сохранение лучшей версии |
| Бесконечные циклы и расходы | Средняя / высокое | Повтор одной ошибки и рост ledger | Reserve до запроса, лимиты по кадру/эпизоду, stop conditions |
| Непереносимость графической среды | Средняя / высокое | Чёрные кадры/driver issues на другом worker | Локальный проверенный профиль; отдельная приёмка новой ОС |
| Дрейф внешности и канона | Средняя / среднее | Случайный skin или изменившаяся роль героя | Fixed asset hashes и CanonPatch только после приёмки |
| Слишком близкое заимствование | Средняя / высокое | Повтор уникального гэга/образа/последовательности | Абстрактные карточки, оригинальные герои, originality review |
| Неподходящие права на исходники/ассеты | Средняя / высокое | Нет provenance или разрешённого использования | Приватное хранение refs, отдельный rights record, проверка перед публикацией |
| Качество держится только на ручной правке | Высокая / критическое | Контрольный прогон требует вмешательства | Отдельно assisted эталон и автономный приёмочный run |
| Экстраполяция 90 секунд на 15 минут | Высокая / высокое | Резкий рост continuity и repair | Масштабировать ступенчато после нескольких успешных пилотов |

Перед публичным выпуском отдельно проверить актуальные [Minecraft Usage Guidelines](https://www.minecraft.net/en-us/usage-guidelines), права на музыку, skins и модифицируемый код. Документ не предполагает, что разрешение на просмотр референса даёт право его публиковать или использовать для обучения.

## 7. Решения до начала программирования

| Решение | Предлагаемый вариант | Что требует подтверждения |
|---|---|---|
| Что считать успешным результатом | Все критерии раздела 3; человеческое понимание важнее автоматического балла | Порог и состав аудитории |
| Первый backend | Отдельный адаптер к pin Minecraft 1.20.4/Fabric/BBS FS, без изменений старого репо | Готовность сопровождать минимальный patch/fork |
| Взаимодействие с миром | Постановочные актёры + небольшой белый список настоящих server events | Обязательно ли реальное inventory/блоковое действие уже в первом пилоте |
| Визуальная свобода | Vanilla world/skins, допускаются умеренные позы в узнаваемом риге | Допустимы ли изменения конечностей/лица; конкретная граница стиля |
| Примитивы и сценарная сложность | 8–12 простых действий; сложные контакты исключить | Набор обязательных действий для первой истории |
| Герои | Два собственных персонажа, не Steve/Alex как финальный каст | Внешность, характеры, отношения, пригодность рига |
| Референсы | 4–6 приватных MP4/фрагментов, два направления отдельно | Какие именно файлы и интервалы, provenance/права |
| API | Настраиваемые роли Sol/Luna; Astra/audio только разрешённо | Доступность моделей в API-проекте и независимый BudgetGrant |
| Начальный cap | Предложение $50: refs $10 + два пилота по $20 | Явное согласование суммы; сейчас не выдано |
| Рабочая станция | Один локальный графический worker; никаких покупок облака | ОС, RAM, доступность рабочего сеанса и зависимости |
| Финальный профиль | 1080p30, 90 секунд как ориентир | 16:9 либо иной формат; решение до camera layout |
| Звук | Событийный foley из разрешённых SFX, без речи | Каталог, лицензии, музыка и допустимые несловесные вокализации |
| Роль человека | Ручная подготовка эталона и финальная приёмка; контрольный run автономен | Что допускается как постоянная редактура после MVP |
| Хранение и публикация | Локальные приватные refs; Git только код/схемы/собственные правила | Репозиторий private/public, retention и разрешённые материалы |
| Организация нового проекта | Самостоятельное приложение + отдельный adapter; старый репо только источник опыта | Название, лицензия собственного кода, состав переноса |
| Масштабирование | Несколько коротких пилотов → 3–5 минут → длинный формат | Условие перехода и повторная оценка бюджета |

Решения можно принять одним пакетом: подтвердить рекомендуемые варианты и перечислить исключения. Подтверждение архитектуры само по себе не подменяет отдельного явного согласия на платный API-бюджет.

**На этом этапе работа останавливается.** Реализация, запуск Minecraft, платный анализ референсов и обучение моделей начнутся только после подтверждения соответствующего следующего этапа.
