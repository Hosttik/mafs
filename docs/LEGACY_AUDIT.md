# Аудит mf_studio

Дата исследования: 26 октября 2026. Репозиторий: [Hosttik/mf_studio](https://github.com/Hosttik/mf_studio).

Изучена ветка `main` на commit **`1adb69d040ebaaffff991d99a4b0129dde54a89e`**. Указанная в ней база BBS FS — `13bd62dab1980b974b8ea0f78d037e8e82684b84`. Это разные идентификаторы: первый фиксирует изученный прототип, второй — его upstream.

## 1. Что именно проверено в этом исследовании

Через GitHub прочитаны README, STUDIO, STUDIO_PLAN, STUDIO_RESULTS, настройки версий, код StudioScene, StudioClient, StudioExportSession, VideoVerifier, Film, Python CLI и lifecycle-проверки, JSON приёмки и окружения. Просмотрено дерево файлов: 2294 записи, ответ GitHub без усечения.

Разделяем уровни доказательств:

- **Виден код:** функция реализована в изученном snapshot.
- **Есть сохранённое свидетельство:** отчёт или лог предыдущего запуска утверждает результат.
- **Перепроверено сейчас:** в этой работе только чтение и сопоставление исходников/отчётов. Сборка, проигрывание видео, контроль хешей бинарных артефактов и запуск Minecraft заново не выполнялись.

Наличие MP4 и contact sheet установлено по дереву репозитория; содержание этих бинарных файлов здесь не просматривалось. Поэтому визуальную выразительность по этому аудиту нельзя считать независимо подтверждённой.

## 2. Работоспособные решения и границы свидетельств

| Решение | Что найдено | Как использовать |
|---|---|---|
| Сцена внутри Minecraft | В StudioScene создаются два Replay/MobForm с ванильными моделями; FilmManager сохраняет и загружает фильм | Основа адаптера к движку, а не генератор истории |
| Программное управление | StudioClient принимает JSON из файловой очереди; CLI создаёт задания атомарно | Сохранить принцип локальной очереди и статусов |
| Камера и актёры | StudioExportSession использует часы WorldFilmController, прогрев и возврат к началу | Перенести с проверкой на новой сборке |
| Запись | В acceptance.json два успешных экспорта: 960×540, 30 fps, 360 кадров, 12 секунд, exit code 0 | Технический исходный уровень, не готовность к 1080p и длинным сценам |
| Проверка файла | ffprobe + полный decode FFmpeg; VideoVerifier сверяет размер, fps, длительность и кадры | Переиспользовать независимо от BBS |
| Сбои и восстановление | Код/отчёты содержат отмену, таймауты, ранний отказ FFmpeg, watchdog, следующий успешный экспорт | Сохранить как приёмочные сценарии нового адаптера |
| Идемпотентность | Повтор id не перезаписывает MP4; незавершённые claimed-задания после аварии становятся failed | Сохранить, добавить проверку хеша запроса при совпавшем id |

Источники: [StudioScene](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/src/main/java/mchorse/bbs_mod/studio/StudioScene.java), [StudioExportSession](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/src/client/java/mchorse/bbs_mod/studio/StudioExportSession.java), [acceptance.json](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/evidence/acceptance.json), [проверка жизненного цикла](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/scripts/check_live.py).

## 3. Что ограничивает постановку

1. **Сцена зашита в Java.** TICKS=240, FPS=30, два персонажа, одна траектория камеры, заданные повороты и кивки. StudioScene.validate требует именно эту форму. Произвольной раскадровки этот контракт не принимает.
2. **Экспорт тоже знает фиксированную сцену.** StudioClient проверяет 360 кадров и 960×540. Длительность и параметры должны приходить из RenderRequest, а не из констант демо.
3. **В показанном прототипе нет сценарного/режиссёрского слоя.** Очередь содержит действие run/generate/export и координаты, но не цель зрительского понимания, драматическую причинность или требования к видимости ключевого действия.
4. **Актёры визуальные.** Документация прямо ограничивает прототип клиентскими replay без взаимодействия с серверными блоками/инвентарём. Возможности server playback в BBS шире, но их наличие в движке не означает приёмку в прототипе.
5. **Аудио отключено.** StudioExportSession выставляет videoExportAudio=false, videoExportMinecraftSounds=false и `-an`. Требуется отдельный звуковой конвейер.
6. **Выразительность ограничена испытанным набором.** Координаты, повороты, кивки и штатная ходьба не доказывают качество жестов, контакт рук с предметами или читаемую игру эмоций.
7. **Успех задания технический.** Валидный MP4 не доказывает наличие конфликта, понятность действия, корректность монтажного стыка или интересность.
8. **Смешаны обязанности runtime.** В StudioClient находятся очередь, запуск мира, перестройка площадки, воспроизведение, экспорт и верификация. В новом проекте orchestration и медиапроверки следует вынести из игрового клиента.

Это ограничения изученного прототипа. Они не доказывают, что именно этот код вызвал все неудачи предыдущих творческих экспериментов: их сценарии, версии, видео и оценки здесь не представлены.

Источник: [StudioClient](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/src/client/java/mchorse/bbs_mod/studio/StudioClient.java), [описание границ](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/docs/STUDIO.md).

## 4. Ошибки, которые нельзя повторять

| Сохранённый опыт | Требование нового проекта |
|---|---|
| Первое видео оказалось чёрным из-за точки захвата framebuffer | Техническая и визуальная верификация независимы; проверять реальный захваченный кадр после blit |
| Yaw BBS отличается от ванильного на 180° | Преобразование координат только внутри backend; независимые испытания реального ракурса |
| Отдельные часы камеры уводили её относительно актёров | Общий production clock; прогрев не продвигает содержимое дубля |
| Старый recorder сохранял результаты предыдущей сессии | Каждый результат связан с take_id, request_hash и текущим процессом |
| Ошибки/частичная запись FFmpeg могли скрываться | Exit code, watchdog, число кадров, full decode и атомарная публикация результата |
| Нулевой счётчик кадров блокировал обработку ранней ошибки | Игровой поток продолжает обрабатывать отмену и завершение даже до первого кадра |
| Автоматизация не была headless | Графический worker указывать явно; не обещать рендер на обычном CPU CI |

Подробности и предыдущие свидетельства: [STUDIO_RESULTS](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/docs/STUDIO_RESULTS.md). Здесь эти сбои не воспроизводились заново.

## 5. Ограничения стека

- В snapshot: Minecraft 1.20.4, Fabric Loader 0.16.14, Fabric API 0.91.3+1.20.4, Java 17 для игры; отчёт указывает Java 21 для Gradle/Loom. Это зафиксированная совместимая комбинация старого проекта, не рекомендация обновить компоненты по отдельности.
- Film/Replay/экспорт не входят в обещанный стабильный addon API. Изоляция за собственным интерфейсом обязательна; при необходимости потребуется сопровождаемый patch/fork в **новом** проекте.
- Отчёт охватывает macOS, Apple M3 Pro и графический сеанс WindowServer. Windows, Linux, dedicated server, multiplayer и отдельный launcher-профиль не прошли указанную приёмку.
- Общие часы клиента не доказывают синхронизацию integrated server, частиц, физики и звуков. Это отдельный эксперимент нового MVP.
- Повторяемость не равна побитовому совпадению файлов: два сохранённых MP4 имеют разные SHA-256. Новая приёмка должна сравнивать события, позы и кадры с допусками, а не требовать одинаковый MP4.
- Headless-render нельзя вывести из автоматического запуска без ручного ввода.

Источники: [gradle.properties](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/gradle.properties), [environment.json](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/evidence/environment.json), [инженерный план](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/docs/STUDIO_PLAN.md).

## 6. Решение о переиспользовании

**Перенести после отдельных проверок:** EncoderPipe/VideoVerifier, принципы StudioExportSession, преобразование камеры, ограничение кадров, сохранение/загрузку фильма, очередь, статусы, watchdog и сценарии отказов.

**Перепроектировать:** StudioScene в компилятор постановки; константы записи в RenderProfile; StudioClient в узкий игровой worker; технический succeeded в отдельный результат записи, не в «эпизод принят».

**Создать заново:** Character Bible, причинную модель истории, библиотеки приёмов, Director, capability registry, preflight, план монтажа/звука, критиков, контроль бюджета и ограниченное исправление.

Старый репозиторий не нужно перемещать, изменять или удалять. В новый проект переносится минимальный выбранный код с сохранением уведомлений из [LICENSE.md](https://github.com/Hosttik/mf_studio/blob/1adb69d040ebaaffff991d99a4b0129dde54a89e/LICENSE.md); происхождение каждого перенесённого файла фиксируется. Публичная выкладка материалов приватного старого проекта требует отдельного решения о составе публикации.
